# AgentTeam · 多智能体协作完成毕业设计

华为 ICT 大赛云赛道 **赛题12（AgentTeam-多智能体协作完成毕业设计）** 的参评作品。

四个角色 Agent 组成一个团队，由主控按 **规划 → 检索 → 写作 → 审校 →（不合格回炉）** 的流水线协作产出一篇毕业论文的完整方案。零第三方依赖，可直接跑。

## 团队分工

| 角色 | 职责 | 产出 |
|:--|:--|:--|
| **规划** Planner | 把"写毕业论文"拆成 5 章大纲 | `outline`（章节标题 + 每章要回答的问题） |
| **检索** Retriever | 为每章准备论据清单 | `briefs`（每章该引用什么、该给什么证据） |
| **写作** Writer | 按大纲 + 论据产出草稿 | `drafts`（每章写作要点 + 目标字数） |
| **审校** Reviewer | 挑逻辑与篇幅问题，给结论 | `verdict` 通过/需修改 + `issues` 列表 |

## 为什么这样切分

多智能体最容易犯的错是**角色重叠**（写作也做检索、审校也做规划），最后没人真正负责。这里的边界是：

- **规划不写内容**，只给结构和每章要回答的问题
- **检索不评价好坏**，只给可用论据
- **写作不做事实核查**，只保证成文
- **审校不改稿**，只输出问题和结论，由主控决定是否回炉

职责单一，才能把"人的判断"放在设计决策上。

## 编排逻辑

```python
Orchestrator(max_rounds=2).run(task)
# 第 1 轮：规划 → 检索 → 写作 → 审校
# 若审校 verdict == "需修改"，第 2 轮只重跑 写作 → 审校（不重新规划）
# 最多 max_rounds 轮，避免死循环
```

**回炉时不重跑规划**是刻意的：大纲没问题就不该推翻，只改内容。这也是多智能体编排里省 token 的关键。

## 消息总线

Agent 之间不直接调用，而是把 `Message` 追加到共享 `context`，下游 Agent 自己从 context 里找上游产出：

```python
@dataclass
class Message:
    sender: str      # 谁说的
    role: str        # 角色名
    content: str     # 人类可读摘要
    meta: dict       # 结构化载荷（outline / briefs / drafts / issues）
```

好处：加一个 Agent（比如"查重"）不用改其他 Agent，只要在 `context` 里读它需要的东西。
